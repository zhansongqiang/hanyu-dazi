十二、订正 §十一：行数之差不是「空行口径」，是我的量具坏了

12.1 §十一 里那条计数提醒**作废**。

  §十一 我写的是：`Measure-Object -Line` 不计空行 ⇒ 我 143 / 7d 282，
  「两者是同一份文件，只是数法不同」。**这句归因是错的。**

12.2 7d 当场用字节反驳我；他们的读数我复算为真：

  PLAN/content.md
    byteLF（0x0A 计数）  = **282**
    byteCR（0x0D 计数）  = **0**
    ReadAllLines(UTF8)    = **282**（其中非空 **239**）
    Get-Content 默认       = 162
    Measure-Object -Line   = 143

  没有 CR ⇒ 任何「换行约定」都变不出 143 与 282 之间那 139 行的差。
  而且**非空 239 ≠ 143** ⇒ 「不计空行」这个解释自相矛盾，当场死掉。
  ⇒ **7d 的 282 是对的；我的 143 作废。「两者只是数法不同」也不成立。**

12.3 真实根因（我上盘实测，非推断）：

  PowerShell **5.1.26100.10068**；
  `[System.Text.Encoding]::Default.WebName` = **gb2312**（本机默认代码页）。
  这两份证据件是 **UTF-8**。
  **裸写 `Get-Content <路径>`（不带 -Encoding）按 gb2312 解码**：
  UTF-8 汉字的多字节序列里，某些尾字节会与紧随其后的 **0x0A 拼成一个
  GB2312 双字节字**，于是那个换行被**当数据吃掉**，两行并成一行。
  ⇒ 不是「数法不同」，是**读的时候字节被工具改写了**。

  现场取证（同一份文件、同一台机器、同一时刻）：
    Get-Content <f>                    -> 一行里出现
                                          「出证人：be-api（…hanyu-dazi-7d）落盘：2026-11-24 14:1x」
                                          两行被并成 1 行
    Get-Content <f> -Encoding UTF8     -> 恢复成 2 行

12.4 结论**保留**，但换一个更强的理由：

  「判同一份文件只认**字节 + md5**，行数不能作身份」
  —— 这条仍然成立，但**不是因为空行口径不同**，
  而是因为**这台机器上的裸 `Get-Content` 会静默吞掉 0x0A**。
  行数连「同一份文件的规模」都表示不了，更别说身份。

  ⇒ 后面凡报行数，一律用 `[System.IO.File]::ReadAllLines($p,[System.Text.Encoding]::UTF8)`
     或 `Get-Content -Encoding UTF8`；裸 `Get-Content` 的读数**不得进任何台账**。

12.5 一条我自己的红线（复现提醒，别再犯）：

  我曾拿 `0x85`（NEL）原始扫描当换行证据，测出 61 / 146 —— 那些是
  **UTF-8 汉字的续字节**，不是分隔符。**原始字节扫描找不出换行，只能数 0x0A。**
  现场无 0x0C / 0x0B / 0x1C-0x1E 中的任何一个。
