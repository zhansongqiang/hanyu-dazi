一、方法（命令逐条给出，任何人可复算）
====================================================================

1.1 三件套取值（PowerShell）

    $x = Get-Item <路径>
    $x.Length                                  # 字节数
    $x.LastWriteTime.ToString('yyyy-MM-dd HH:mm:ss.fffffff')   # 纳秒 mtime
    (Get-FileHash <路径> -Algorithm MD5).Hash.ToLower()         # md5

1.2 写集判别（内容判别器，不用 mtime）

    git status --porcelain -- server/src
    git ls-files server/src                                        # 已跟踪
    git ls-files --others --exclude-standard server/src            # 未跟踪
    # 逐件判「与 028de6a 是否同内容」：
    foreach ($f in (git ls-files server/src)) { git diff --quiet HEAD -- $f; $LASTEXITCODE }

  注：git 会打 LF->CRLF 的 warning，那是 autocrlf 提示，不是内容差异，读时忽略。

十一、订正 §八：行数之差不是「空行口径」，是我的量具坏了
====================================================================

11.1 §八 里那组读数**作废**。

  §八 我写的是：7d 报 241 行；我实测 156（Get-Content 全部）/ 127（Measure-Object -Line）；
  「同一份文件，只是空行口径不同」。**归因错了。**

11.2 7d 当场用字节反驳我：「你那个能数成 156 的量具，把 241 数成 156，差 85 行，
     若落进台账就没人能复算」。我复算他们的读数，**他全对**：

  PLAN/evidence/be-api-lane-pins.txt（当时 14626 B 那一版）
    byteLF = **258**，byteCR = **0**
    ReadAllLines(UTF8)    = **258**（非空 **199**）
    Get-Content 默认       = 166
    Measure-Object -Line   = 137

  没有 CR ⇒ 「换行约定」这条解释根本不成立。
  且 **非空 199 ≠ 137** ⇒ 「Measure-Object 不计空行」也自相矛盾。
  ⇒ 7d 是对的；我 §八 的 156 / 127 **作废**。

11.3 真实根因（我上盘实测）：

  PowerShell **5.1.26100.10068**；`[System.Text.Encoding]::Default.WebName` = **gb2312**；
  本件是 **UTF-8**。**裸 `Get-Content` 按 gb2312 解码**，会**吞掉某些 0x0A**
  （UTF-8 汉字尾字节 + 0x0A 被拼成一个 GB2312 双字节字），于是行被合并。
  ⇒ 不是数法不同，是**量具在读的时候改写了字节**。

11.4 结论保留，理由换强：

  §八 的结论「身份只认字节 + md5，mtime 只作时序辅证，行数不得作判据」
  **仍然成立**，但真正的理由不是「空行口径不同」，而是
  **这台机器上的裸 `Get-Content` 会静默吞 0x0A**。
  重复一遍 7d 那句，它说到了点子上：一个能把 241 数成 156 的量具，
  落进台账就是一条没人能复算的旁证。

  规矩（自定，并请编排者采纳）：
    报行数一律用 `[System.IO.File]::ReadAllLines($p,[System.Text.Encoding]::UTF8)`
    或 `Get-Content -Encoding UTF8`；裸 `Get-Content` 的读数**不进任何台账**。
