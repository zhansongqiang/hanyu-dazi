## 环境与方法

**临时库从哪来（重要，别跳过）**：
共享库 `data/hanyu-dazi.db` 主文件只有 254 KB，而 `hanyu-dazi.db-wal` 有 **4.1 MB** ——
也就是说**大部分已提交的数据还在 WAL 里，没并进主文件**。直接 `cp` 主文件会拷到一个残库。
所以用 SQLite 的在线快照，**不停任何进程、不碰共享库**：

    cd server && npx tsx -e "import db from './src/config/database'; \
      db.raw(\"VACUUM INTO './data/tmp-edge.db'\").then(() => db.destroy()).then(() => process.exit(0))"
    # → VACUUM_OK，产物 270336 字节

（这顺带**独立佐证了 CLAUDE.md 里那条教训**：不 checkpoint 就传 `.db` = 丢数据。）

## 逐条判定

### G6 · 8 人上限

- **上限就是 8，且**边界**不越位**：队长 + 第 1..7 个加入者 = **8 人**，
  第 7 个加入者拿到的 `memberCount` **正好是 8 并且成功** —— 这是本轮的**边界断言**（off-by-one）。
  第 8 个加入者（第 9 个账号）→ **HTTP 400 / `code:1` / 「小组已满（上限 8 人）」**。
- **拒绝是原子的、干净的**：被拒的那个账号 `GET /teams/mine` → **`data:null`**，
  没被塞进 `team_members` 留半条。队长视角复核 `memberCount=8`、`members` 8 行、队长带 `isCaptain`。
- **check 读的是源表 COUNT**（`db('team_members').where({team_id}).count()`），
  不是 `teams` 表上的冗余列，所以不会出现"人数显示 8、实际 9"的漂移。

### G5 · 过期语义

- **有效期就是 7 天**：发起时回 `expiresAt="2026-12-01 23:59:59"`，
  恰是发起日（2026-11-24）+ 7 天且落在当天最后一秒，与 `DUEL_EXPIRE_DAYS = 7` 对得上。
- **`expired` 是读时算出来的**，这一点本轮**直接证到了**：把 `expires_at` 改到 2020 年之后，
  库里 `status` **列本身仍是 `open`**（B3），但 `GET /duels/:code` 回 **`status:"expired"`**（B4）。
  也就是说这里**没有定时任务、没有写回**，是 `effectiveStatus()` 在每次读时比一次 `now`。
  这个设计是刻意的：GET 不该拿写锁。
- **过期后 `items` 是 `null`**（B5），不是空数组 —— 与 §4.4「`status != 'open'` 时 `items` 为 `null`」一致。
- **过期后提交被拒**：`POST /duels/:code/submit` → `code:1`「挑战已过期」（B6），
  且**分数没写进去**（B8 复核 `opponent_score` 仍为 `null`）—— 拒绝得干净，不是"先写后回滚"。
- **两个端点同源**：`GET /duels/recent` 里同一行也报 `expired`（B7），
  说明列表页不会拿一个 `open` 的旧值骗用户。

## 证明力边界（写清楚，别放大）

- 过期是**直接改库**构造的，不是真等 7 天 —— 它验的是 **`effectiveStatus()` 对 `expires_at` 的反应**，
  不是"系统到点会自动做什么"（本项目**没有**这种定时任务，也不需要）。
- 8 人上限是**单进程、顺序加入**测的。并发同时加入最后一个空位会不会双双挤进去，
  **本轮没测**（需要并发压测，属另一类验证）；就本项目的使用场景（分享邀请码给同学逐个点进来）
  而言，顺序加入是主路径。
- 全部结论来自**隔离实例 8099 + 临时库副本 + 桌面 HTTP 客户端**，不是打包产物、不是真机。
