1.1 写集怎么定 —— 用内容判别器，不用 mtime
--------------------------------------------------------------------
判据不是「谁在什么时刻写了什么」，而是「哪些字节与 Day 1 存档不同」：

    cd /d/coding/hanyu-dazi
    git log --oneline -1
    git diff --name-only HEAD
    git status --porcelain

读数（2026-11-24 14:16 复算，三次一致）：

    HEAD = 028de6a  chore: git init —— Day 1 收口存档

    M（与 028de6a 内容不同 · 已跟踪）：
        server/src/app.ts
        server/src/routes/index.ts

    ??（028de6a 里根本不存在 · 未跟踪）：
        server/src/services/                          （共 6 件）
        server/src/routes/attempts.ts
        server/src/routes/content.ts
        server/src/routes/progress.ts
        server/src/routes/wrongbook.ts
        server/src/migrations/20261123170000_reports.ts

⇒ be-api 泳道 server/src/** 的写集 = 2 + 6 + 4 + 1 = 13 件。
（git 会顺带打一串 LF -> CRLF 的 warning，那是 autocrlf 的提示，不是内容差异，
  与本判别器无关，读的时候忽略即可。）

为什么用判别器而不是 mtime：
  mtime 只证「何时写入」，证不了「何人写入」；而且复制、解压、编辑器重存都会
  改写 mtime。内容判别器问的是「这份字节与存档是否相同」，得到的是内容事实，
  与时钟无关。

1.2 三件套怎么取
--------------------------------------------------------------------
    cd /d/coding/hanyu-dazi
    for f in <上列 13 件>; do
      printf '%-46s ' "$f"; stat -c '%s  %y' "$f"; md5sum "$f" | cut -c1-32
    done

  stat 的 %s = 字节数；%y = 完整 mtime（含纳秒 + 时区）
  md5sum 的 md5 取前 32 位十六进制
  本卷（NTFS）纳秒精度有效：本表 13 件的秒内小数互不相同，可区分不同次写入。

    最晚  16:58:58   server/src/routes/attempts.ts

⇒ be-api 泳道 server/src/** 的**最后一次写入**是 2026-11-23 16:58:58，

推论（这才是本件要钉住的那句）：
  我的验收跑发生在 11-24 11:0x-11:20，而验收对象源件的最后写入是

  所以缺口不是「对象不符、只缺哈希」，而是「**对象既符、哈希也在**」。
  换言之：验收对象与部署对象是同一批字节，此前只是缺一个可复算的身份。

5.3 md5 证不了的事（如实记）
--------------------------------------------------------------------
  - md5 证「这批字节是什么」，**证不了「谁写的」**。
    署名按当事方自陈记（编排者 12:2x 已把这条写成 GV-04）：
    自陈不等于磁盘证得。本件的价值在「字节身份」，不在「作者身份」。
  - mtime 证「何时写入」，同样证不了「何人写入」。
  - 三件套只覆盖 server/src/**。本轮 be-api 泳道未向 mobile/** 或
    server/content/** 写入（那三处属 fe-learn / fe-game / content）。

5.4 一处复算提示（与他方读数对齐用）
--------------------------------------------------------------------
  液相夹具库里 stroke 那 28 行的 options 列是 SQL NULL。
  凡口径先做 String(v) 的，String(null) === 字符串 null，会**不可区分**。
  本泳道在内容指纹上用的口径 A 是 JSON.stringify(行对象)，
  better-sqlite3 把 SQL NULL 渲染成 JSON 的 null 字面量，
  是**确定性**的，不受此坑影响 —— 记在这里只为与别人换实现时对齐。
