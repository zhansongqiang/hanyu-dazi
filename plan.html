汉语搭子

搭

学完课本，来这儿找人练。

给北语留学生的中文课后陪练社区：系统课程打底，真人 PK 与人味社交收口。方案已定稿——开发全程在本机跑通闭环，第一天晚上把上线链路演练一遍，第五天交链接。下面是全部决策、五天排期和答辩预案。

  • 5 天
  • 1 个人
  • 交付一个链接
  • 底座复用 ~65%
  • 手机优先 H5
  • 本地开发优先
  • 独立租户 · 不碰现有平台

一已经定下来的十五件事

这些是你我逐条敲定的结论，后面所有内容都从这里长出来。任何一条要改，直接改这一条，不用重读全文。

  1. 01形态：H5 网页，交链接课程作业要交链接，免安装、跨设备、当场可演示；用 uni-app 打包，同一套代码随时能出 APK。
  2. 02前端：uni-app + Vue3 + TypeScript + Vite直接复用兄弟项目 habit-arena 的 mobile/，端口、请求封装、鉴权、页面骨架都是现成的。
  3. 03后端：Express + TypeScript + Knex + SQLite单文件数据库，一个人维护成本最低，服务器上不用装 MySQL。
  4. 04底座复用约 60–65%登录鉴权、打卡、连击、组队、排行榜、成就六块直接用，省下的时间全部投到内容与游戏化。
  5. 05内容分层：基础 / 进阶 / 拓展 × 字 / 词 / 句 / 对话你原话的四层结构保留，落到 units 的两个维度上，界面用两级筛选呈现。
  6. 06首版内容 60–80 个知识点，写死在 content.json5 天做不出内容后台。内容以代码文件形式发布，扩充等于改文件重部署。
  7. 07PK 做成异步：挑战码 + 分享链接 + 免注册游客实时对战要 WebSocket、匹配、并发，一个人五天做不完。异步同样能跨设备真人对战，且对方不用注册。
  8. 08游戏化：连击 / XP / 印章 / 科举段位周榜只做奖励，不做惩罚。不照搬 Duolingo 的心——掉心机制和「每天来打卡」的目标直接冲突。
  9. 09笔顺描红：hanzi-writer + 米字格，只做 12 个象形字日、月、山、水、人、大、小、上、下、中、口、火。这是竞品没做的东西，成本却很低。
  10. 10发音音频预生成 mp3；「说」这一块 v1 争取做成跟读录音 + 回放自评不用运行时浏览器语音合成：安卓 WebView 支持不全、中文本地音色不稳定，演示会翻车。跟读录音则做成录 → 存 → 回放 → 自评四步，麦克风的两头条件本来就都具备：本地开发时 localhost / 127.0.0.1 本身就是安全上下文，上线后入口又是 https://。仍然不做的是「智能评分」——不接语音识别服务，判对错的是学习者的耳朵，不是算法，这样评分口径不需要设计，也不引入外部依赖。作为本版唯一的争取项，它排在收尾日、主线之后，进度紧就整体让位。理由与排期见第十二节第五点。
  11. 11内容口径：对齐 HSK 3.0 三等九级框架，首版是样本切片不硬吹「完整课程」。见第八节的答辩原话。
  12. 12视觉：宣纸 / 朱砂 / 墨 / 泥金，宋体标题，回纹点缀中国元素靠材质和留白，不靠堆砌龙纹祥云。
  13. 13开发全在本地，上线是第二阶段，挂 zj17z.cn（114.132.232.60）的子域名开发阶段不碰服务器：本机起 Express 8091 + SQLite + Vite 热更新，改一行就看得见。上线那天挂在自己的子域名 hanyu.zj17z.cn 上——这台机器跑着 SmartCampus 的生产环境（PM2 smartcampus 占 8080、smartcampus-demo 占 8082），学校在用它，所以我们只做加法：独立目录、独立端口、独立 PM2 名、独立 nginx vhost、独立数据库文件，一个都不重叠。机器上 certbot 与自动续期都是现成的。链路在 Day 1 晚上先走通一次空壳，之后每次上线只是重传构建产物。
  14. 14社交安全：举报入口 + 好友限定私信 + 未成年人默认关闭有真人社交就必须有这套设计，v1 只做举报与用户资料，不做聊天。
  15. 15策略：宽度优先，每天一个能演示的里程碑宁可砍功能，不砍闭环。断链的功能比少一个功能更伤答辩。

二范围边界：做什么，不做什么

答辩最容易被问「这个为什么没有」。提前把不做的东西写下来，就不是漏洞，是取舍。

v1 一定做（含一个争取项）

  • 账号注册登录（用户名密码，游客可玩 PK）
  • 三级课程浏览 → 课时 → 答题判分
  • 学习进度与课时完成度
  • 错题本 + 错题重练
  • 每日打卡与连击
  • 笔画描红（12 字）
  • 异步 PK：发起、分享、游客作答、结果对比
  • 组队与周排行榜
  • XP、印章、科举段位
  • 跟读录音 + 回放自评（争取项：收尾日做，进度紧则让位）
  • 中国风 UI 与深色模式

v1 明确不做

  • 实时对战、在线匹配
  • 语音识别评分（判对错的是耳朵，不接识别服务——见第十二节第五点）
  • 内容管理后台
  • 教师端、班级管理
  • 私信与聊天
  • 支付、会员、广告
  • AI 生成课程内容
  • 应用商店上架
  • 超过中英两种界面语言

关于「争取项」：跟读录音是本版唯一的浮动范围。它不是闭环的一环——少了它，「学—错—练—打卡—PK」照样成立；所以它的排期永远排在错题本与 PK 之后，做不出来不影响交付，做出来是答辩上多一个现场动作。

三凭什么有人用：市面上的空位

把同类产品排在一条线上，空位就出来了。课程做得好的不做社交，社交做得好的不做课程。

产品系统课程真人社交笔顺教学口语录音

SuperChinese强无有有
Duolingo 中文课中无无弱
HelloTalk无强无有

别人卖课，我们做课后陪练。真正可能被记住的是笔顺和张口两件事：Duolingo 的中文课根本不教笔顺，而零基础学习者最怕的就是「会认不会写」——选 12 个象形字把描红做扎实，比铺 300 个字做得潦草更有说服力。同一个道理落在「说」上：不去追智能评分，先把「录下来听自己」这一步做起来。这是课程类产品里最容易被跳过的一环，也是跟读法最原本的形态。

一个诚实的边界：我们没有真人语伴的存量，所以「社交」在 v1 里是熟人之间的 PK 与组队，不是陌生人匹配。这也正好符合真实使用场景——同班同学下课后互相较劲。

四谁在用，怎么留下来

用户

北语在读留学生，中文零基础到 HSK 2 级之间，每天愿意花 10–15 分钟。场景是下课后、宿舍床上、食堂排队——都是单手拿手机、随时会被打断的碎片时间。

学习闭环

  1. 学一课：从「基础 · 字」开始，看图认字、选拼音、选意思、描红。
  2. 答错即入错题本：答错的那道题自动进错题本，不需要用户手动收藏。
  3. 打卡续连击：完成任意一课即可打卡，连击天数往上走。
  4. 拉朋友来比：生成挑战码和链接，对方不注册也能答，结果并排显示。
  5. 回错题本重练：错题重练一次即标记掌握。
  6. 回到下一课：进度条推进，下一节课解锁。

这个闭环里每一步都有即时反馈，也都有下一件事可做——这是打卡类产品能留住人的唯一原因。

关键 DDL（开发时照抄） 
CREATE TABLE units (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  level TEXT NOT NULL,      -- basic | advanced | extended
  type  TEXT NOT NULL,      -- char | word | sentence | dialogue
  title TEXT NOT NULL,
  title_en TEXT,
  sort  INTEGER DEFAULT 0
);

CREATE TABLE items (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  lesson_id INTEGER NOT NULL REFERENCES lessons(id),
  kind TEXT NOT NULL,       -- recognize | pinyin | meaning | stroke | listen
  prompt TEXT NOT NULL,
  prompt_en TEXT,
  options TEXT,             -- JSON 数组
  answer TEXT NOT NULL,
  char TEXT,                -- 描红用
  audio_url TEXT,
  sort INTEGER DEFAULT 0
);

CREATE TABLE attempts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL,
  item_id INTEGER NOT NULL,
  lesson_id INTEGER NOT NULL,
  is_correct INTEGER NOT NULL,
  user_answer TEXT,
  duration_ms INTEGER,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_attempts_wrong ON attempts(user_id, is_correct, item_id);

-- 错题本：不建表，只建视图
CREATE VIEW wrong_book AS
SELECT a.user_id, a.item_id, COUNT(*) AS wrong_times,
       MAX(a.created_at) AS last_wrong_at
FROM attempts a
WHERE a.is_correct = 0
GROUP BY a.user_id, a.item_id;

CREATE TABLE duels (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  code TEXT UNIQUE NOT NULL,       -- 6 位挑战码
  lesson_id INTEGER NOT NULL,
  challenger_id INTEGER NOT NULL,
  challenger_score INTEGER,
  challenger_ms INTEGER,
  opponent_name TEXT,              -- 游客只留名字
  opponent_score INTEGER,
  opponent_ms INTEGER,
  status TEXT DEFAULT 'open',      -- open | done | expired
  expires_at TEXT
);

-- 争取项：跟读录音。音频文件落 uploads/recordings/，表里只存元数据
CREATE TABLE recordings (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL,
  item_id INTEGER NOT NULL,
  file_path TEXT NOT NULL,         -- 相对 uploads/recordings/ 的文件名
  duration_ms INTEGER,
  size_bytes INTEGER,
  self_rating TEXT,                -- like | close | off（自评，三档）
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_recordings_user ON recordings(user_id, item_id);

注意 duels 里的 opponent_name：对手是免注册游客，只存一个名字和分数，没有 user 记录。这是「分享链接给同学，他不用注册就能跟你比」这个体验的代价，也是有意的设计。

录音（争取项）为什么只存路径不存二进制：往 SQLite 里塞音频会让单文件数据库迅速膨胀，也会拖慢 .db 的备份上传。音频放 uploads/recordings/ 独立目录，库里只留元数据；用户要删就删文件加删行，不牵动别的表。单条时长与体积在接口层设上限，避免五天的演示把磁盘写满。

八内容口径：怎么讲才不会被问倒

这是整个方案里最容易翻车的地方，先把数字摆清楚。

  • HSK 3.0 是三等九级：初等（1–3 级）、中等（4–6 级）、高等（7–9 级）。
  • 一级要求约 300 个汉字、500 个词。
  • 首版 60–80 个知识点，大约是一级的 12–16%。

所以不要说「涵盖 HSK 一级」。答辩原话建议这样说：

「内容框架与 HSK 3.0 的三等九级对齐，题目类型覆盖认字、拼音、词义、笔顺、跟读五类指标。首版 60–80 个知识点是用来验证学习闭环的样本切片，不是完整课程——把闭环跑通是这一版的目标，扩充内容是数据活，不是开发活。」

这个口径的好处是：它承认了量少，同时把「量少」解释成一个有意识的选择，而不是没做完。老师问「为什么这么少」，你答的是设计决策，不是借口。

九游戏化：奖励，但不惩罚

多邻国和中文学习的目标在这里是冲突的。多邻国的「心」是防止你一次刷太多，代价是答错就罚、答错就退出——而我们要的是每天来、每次都答错得起。所以只留奖励。

机制怎么做来自
连击每天完成任意一课即续连击；断了清零但保留最长纪录复用 habit-arena

段位用科举而不是青铜白银，是中国元素里少数既有辨识度又真的贴合「进阶」含义的东西——它本身就是一套考试等级，拿来当学习段位不需要解释。

十二开发与部署纪律

分两段：开发阶段全在本机，只有五条本地规矩；上线是第二阶段，Day 1 晚上第一次执行，纪律全部来自那台机器的实测情况。

一、本地开发纪律（现在生效）

  • Windows 上 tsx watch 不可靠，改完后端必须手动重启：先 netstat -ano | findstr :8091 找到 PID，再 taskkill //PID <pid> //F，然后重新起。依赖热重载会出现「明明改了却没生效」的假象，专坑排查时间。
  • 本地后端端口也用 8091，与线上完全一致。上线那天配置里一个数字都不用改。
  • 数据库是本地文件 server/data/hanyu-dazi.db，Knex 迁移在本地跑。上线时把这个文件拷过去即可，也可以重新初始化后只灌演示数据。
  • 本地限流同样是每分钟 5 次登录。开发时反复测登录会把自己锁在门外——健康检查用 /api/health 或单元列表，别用登录。
  • 想用手机看效果：Vite 加 --host，手机访问 http://192.168.x.x:5173。注意这是局域网 IP，不是安全上下文——麦克风与 PWA 在手机上要等 Day 1 上线之后才能测，本地只能在电脑浏览器里验。

以下五节属于第二阶段，本地开发阶段不适用。内容都是在 114.132.232.60 上实测出来的，Day 1 晚上第一次上线时照此执行，不要临场发挥。

二、上线 · 隔离：只做加法

zj17z.cn（114.132.232.60）上跑着 SmartCampus 的生产环境，学校在用。这台机器上任何一个粗暴动作，坏的都不只是它自己。以下每一条是硬约束，不是建议。

  • 独立目录 /home/ubuntu/hanyu-dazi/，不放进 smartcampus/ 里面，也不共用它的 server/data/
  • 独立 nginx vhost /etc/nginx/sites-available/hanyu-dazi，server_name hanyu.zj17z.cn，不加 default_server
  • 独立 PM2 应用名 hanyu-dazi，环境变量写在 ecosystem.config.js 的 env 字段里（不依赖 .env，PM2 的 cwd 可能不是项目根）
  • 独立 Node 端口 8091（实测空闲），只绑 127.0.0.1，公网只经 nginx 的 443 进来
  • 独立 SQLite 文件 hanyu-dazi.db，绝不指向 smartcampus.db
  • 独立 JWT 密钥，不用现有平台的任何密钥

绝对不做：pm2 kill / pm2 delete all / pm2 stop all（会打死 smartcampus 与 demo）、pm2 flush（清掉学校平台的日志）、删 /home/ubuntu/smartcampus、改或改序 /etc/nginx/sites-enabled/smartcampus、在 sites-enabled/ 里加 default_server、把备份文件落进任何 nginx web root（/var/www/html 也不行）。~/webroot-bak-* 是现有站点发布时的备份目录，不要碰。

还有一个具体的坑：sites-enabled/smartcampus 是一个手改过的普通文件（3561 字节），和 sites-available/ 里那份 2001 字节的旧拷贝已经不一致了。也就是说，任何时候只要有人用 sites-available 那份重新软链过去，线上配置就会回退。我们不去动它、也不「顺手同步」它——它不属于这个项目。

三、上线 · 构建在本地，服务器只负责启动

3.39G 内存、没有 swap、还跑着约 1.1G 的生产应用——在服务器上 npm install 再打包，轻则把现有应用拖慢，重则 OOM 把它打死。所以：前端 vite build 一律在本机完成，只上传 dist/；后端上传源码后在服务器跑一次 tsc 就够了（这个量级没问题）。npm install --production 要单独装 typescript，否则 tsc 根本不存在。数据库文件上传前必须先停后端做 WAL checkpoint，否则传上去的是旧数据。

四、上线 · 访问入口：子域名 + 443，一个端口都不用开

这台机器的 80/443 已经被 smartcampus（server_name zj17z.cn www.zj17z.cn）和 smartcampus-demo（server_name demo.zj17z.cn）用着，而且 certbot 已经装好、续期定时器在跑。所以「再挂一个站点」在这里的正确形态是第三个子域名，而不是新开端口。

Day 1 晚上要做的（一遍做完）

  • DNSPod 加一条 A 记录：hanyu → 114.132.232.60（这一步是你来做）
  • 复制 sites-available/smartcampus-demo 成 sites-available/hanyu-dazi，改 server_name 与 root
  • 软链进 sites-enabled/，文件名排在 smartcampus-demo 之后（见下方注意事项）
  • sudo nginx -t && sudo systemctl reload nginx（reload 不断开现有连接）
  • sudo certbot --nginx -d hanyu.zj17z.cn，它会自己把 443 块和 80→443 跳转写好
  • /api/ 反代到 127.0.0.1:8091，SPA 用 try_files $uri $uri/ /index.html

因此白拿到的

  • 零防火墙改动：ufw 只放行 22/80/443，安全组也是——正好够用
  • 零端口操作：不用去控制台，也不用 ufw allow
  • HTTPS 观感：https:// + 小锁，答辩现场交链接更体面
  • 麦克风权限可用：安全上下文成立，录音不再是「API 拿不到权限」的死路
  • PWA 离线可用：service worker 只在 HTTPS 下注册
  • 裸 IP 与 zj17z.cn 的请求仍精确命中 smartcampus，不抢现有流量

有一件事要提前知道：同一个 listen 上「Host 谁都匹配不上」的请求，nginx 会给第一个 server 块，而 sites-enabled 是按字母序 include 的。现在里面有 smartcampus 和 smartcampus-demo，所以 smartcampus 事实上是 80/443 的兜底块（这也是为什么访问裸 IP 能打开主站）。hanyu-dazi 按字母序排在 smartcampus 前面，直接软链过去会把兜底角色抢走，裸 IP 的访问行为就变了。所以软链名要选一个排在 smartcampus-demo 之后的名字，比如 zz-hanyu-dazi；sites-available/ 里的文件名保持 hanyu-dazi 不变。这不是洁癖——裸 IP 是现有平台的入口之一，改它就是在改别人的站点。

五、录音：v1 争取做的是「回放自评」

门槛这一层早就没有了——入口就是 HTTPS，本地开发又跑在 localhost 上，两边都是安全上下文，getUserMedia 在本地就能拿到权限、录出声来。所以录音不是被技术挡住的，是被排期限住的。

v1 争取把它做出闭环，四步齐全，只是最后一步交给人而不是机器：录（前端 MediaRecorder，跟在 kind = 'listen' 的题目后面给跟读提示）→ 存（multer 落盘到 uploads/recordings/，库里只留一条元数据）→ 放（回放给自己听）→ 评（自评三档「像 / 接近 / 不像」，一次点击，不接任何识别服务）。

「评」这一层刻意做成自评，是这套方案里最划算的一刀：一旦改成自动评分，就要接入第三方语音识别、设计评分口径、处理网络超时与额度，等于凭空多一条外部依赖和一条失败路径——而这五天最不能出的就是这种岔子。判对错的是学习者的耳朵，不是算法；这一点在答辩里站得住，因为自己听自己就是跟读法原本的形态。

排期位置：录音是这五天里唯一的浮动范围——Day 5 打磨与内容扩充之后再做，进度紧就整体让位。它不算闭环的一环：少了它，「学—错—练—打卡—PK」照样成立。所以它也不进 Day 1–4 的任何里程碑，做不出来不影响交付。

答辩说法：「录音我们做了——录、存、回放，加自己听自己评。没做的是智能评分：那要接识别服务、定评分口径、还要处理网络和额度，五天里我优先保证学习闭环和 PK 是完整的。自评这一步恰恰是跟读法的原形态，不是简化。」别说成「技术做不到」，也别说成「来不及」——说成有意的分层取舍。

六、上线 · 上线前自检

上线分两次，这份自检两次都要走一遍：Day 1 晚上第一次（把链路打通）和 Day 5 收尾第二次（把成品放上去）。

  • 先存档一次 pm2 list + pm2 jlist，记下 smartcampus 的 pid、uptime、↺ 次数；部署完再跑一次比对——这是这台机器特有的验收项，用来确认我们没影响学校那套系统
  • 部署完先等 60 秒再测登录——限流是每分钟 5 次，部署过程中反复测会打满，用户首次登录直接 500
  • 用非登录接口（如单元列表）验证服务健康，省下登录配额
  • pm2 list 看两次，确认 hanyu-dazi 的 uptime 在涨、↺ 没动
  • curl -s -o /dev/null -w "%{http_code}" https://hanyu.zj17z.cn/ 必须 200；同时 https://zj17z.cn/ 与 https://demo.zj17z.cn/ 也还是 200
  • sudo nginx -t 通过再 reload，不用 restart（reload 不断开现有连接）
  • 证书签好后确认 systemctl list-timers | grep certbot 里还有续期任务，别把别人的定时器搞掉了
  • 传数据库前先停后端做 WAL checkpoint，否则传上去的是旧数据
  • 若这次带了录音：确认 uploads/recordings/ 目录存在且可写，并看一眼 df -h（59G 的盘已用 25G）——录音是唯一会持续长胖的东西，别挤到学校那套的磁盘

十四答辩预案

五分钟讲稿骨架

  1. 问题（40 秒）：北语每年上万名留学生，课上时间有限，课后没人陪练。现有产品要么只有课程、要么只有社交。
  2. 方案（60 秒）：汉语搭子 = 系统课程 + 真人 PK。三级内容结构，答错自动进错题本，打卡续连击，拉同学来比；「说」这一块做跟读录音，录完当场回放给自己听。
  3. 现场演示（150 秒）：见下方杀手锏。
  4. 技术（50 秒）：复用已有项目底座约 65%，五天完成。开发全程在本机跑通，上线是加在现有服务器上的独立租户——独立子域名 hanyu.zj17z.cn、独立端口、独立进程、独立数据库，HTTPS 与自动续期都是现成的；uni-app 一套代码随时能出安卓包。
  5. 诚实边界（40 秒）：内容是样本切片，录音做的是跟读回放与自评、不做智能评分——都明确说清；下一步是扩充内容、补发音评分与语伴匹配。

杀手锏演示

提前在自己的手机上打开「创建挑战」，现场请老师拿出手机扫你的分享链接——他不用注册，输一个名字就能答题。他答完，他的分数立刻出现在你屏幕的结果对比页上。

这个动作同时证明了四件事：链接真的在跑、免注册体验成立、跨设备真实生效、后端写入正常。比任何 PPT 都有说服力。

第二个动作（录音做完才有）：随手点开一道跟读题，现场录一句、立刻回放——证明「说」这条链路是真的通的，而不是界面上摆了个麦克风图标。

预设问答

这和多邻国、HelloChinese 有什么不一样？

它们卖课，我们做课后陪练。两个具体差别：一是我们把同班同学之间的 PK 做成核心动作，它们没有真人社交；二是笔顺描红，多邻国的中文课根本不教笔顺，而零基础学习者最怕会认不会写。

内容才几十个知识点，太少了。

对，这是有意的。框架跟 HSK 3.0 三等九级对齐，首版是验证学习闭环的样本切片。这一版的目标是把「学—错—练—打卡—PK」这条链跑通，扩充内容是数据活，不是开发活。

真人社交怎么保证安全？

v1 没有私信，也没有陌生人匹配——PK 是通过分享链接在熟人之间发生的。有举报入口和用户资料页，未成年人账号默认关闭私信这条已经在数据模型里预留。

为什么用网页而不是原生 App？

五天内一个人做完，网页是唯一能按时交链接的方案，而且免安装、跨 iOS 和安卓。用的是 uni-app，同一套代码随时能打包成安卓 APK，不是技术选型上的妥协。开发阶段也走网页这条路——改一行代码浏览器里立刻就是新版，不用每改一次都打包、上传、重启。

为什么先在本地跑，不一开始就部署？

这是把部署拆成「一次演练 + 一次执行」，不是把它推到最后一刻。开发期在本机开着两个进程就能跑完整个闭环，省掉编译、上传、重启那一圈，改一行看一眼；同时上线链路该踩的四个坑——域名解析、nginx 配置、证书签发、进程托管——在第一天晚上就拿一个空壳走通一遍，所以到交作业那天，上线只是把构建产物重新传一次，不是第一次尝试。换句话说，本地优先降低的是每天的摩擦，不是交付标准。

PK 为什么不做成实时的？

实时对战需要 WebSocket、匹配机制和并发控制，一个人五天做不完，而且留学生很难约到同时在线。异步挑战码反而更符合真实场景——你下课后发起挑战，同学晚上有空再答，结果照样并排显示。

数据是真的还是造的？

现在当场做一次。您刚才答的那道题，现在就在数据库里。要不要我再打开错题本给您看？

为什么不是自己的域名和独立服务器？

因为这台服务器是我手上已有的资源，上面还跑着一套在用的学校平台，所以我按「独立租户」的方式挂上去：独立子域名、独立 nginx 配置、独立进程、独立端口、独立数据库文件，一个都不与它重叠。运维上是加法，不是改造。真要有自己的域名，改一条 A 记录就切走了，代码一行不用动。

为什么录音只做回放，不做实时评分？

因为真正难的不是录音，是评分口径。麦克风拿得到、录和放都是浏览器原生能力；一旦要自动判分，就得接识别服务、定评分标准，还得处理网络超时和准确率——那是把五天里最不确定的东西塞进主线。跟读场景里「自己听、自己判像不像」本来就是标准做法，不是缩水版。实时评分我排在下一版，到时候是加一个接口，不动架构。

这块用了 AI 辅助开发吗？

用了，代码实现和方案梳理都有 AI 参与。产品决策、内容取舍和这套设计语言是我定的。这本来也是现在开发者的真实工作方式。

下一步打算做什么？

三件事：一是把内容从样本切片扩到 HSK 一级全覆盖；二是给录音接上实时评分（识别服务 + 评分口径）；三是做语伴匹配，让 PK 从熟人扩展到同水平的学习者之间。技术上都不需要改架构。
